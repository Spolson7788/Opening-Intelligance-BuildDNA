# Facility condition/lifecycle evidence — local implementation

Extends deployed fbdf24e without live changes. New GET /api/condition-history/facility/:openingId reads an authorized facility in one repeatable-read read-only snapshot. The existing owner/provider tenant predicate is applied to the anchor and selected openings. No schema migration, new credentials, grants, RLS changes or write endpoint.

The separate Facility Dashboard history page groups exact saved records by opening: current assessment, retired physical instances, original condition observations and correction chains, installation facts, legacy unreviewed dates, lifecycle/warranty/downtime records, positions, replacements and original service events. Each service row appears once by original ID; no financial or downtime aggregation across openings. Unknowns stay unknown. Raw recorded dates are sorted for display without calculating recency, exposure or reliability. No manufacturer aliases, historical backfill or inferred coverage. This is distinct from the facility financial sandbox export.

The export uses the saved snapshot's original as-of time. Account/token changes, stale responses, refresh/export races, failed loads, foreign-opening rows and duplicate IDs fail closed. UI detail rows are rendered lazily after grouping. Maximum 1000 openings and 10000 rows per evidence table; larger reports fail explicitly rather than truncate. No hosted large-facility performance claim.

## New user policy requirements — reconciled, not implemented or activated
Purchasing authority must be explicitly assigned to specific facility accounts identified by verified email; generic admin membership is not purchasing authority. Future design must bind assignment to stable user ID + facility, retain email as reviewed identity evidence, distinguish assignment administration from spending authority, and audit grant/revoke. No real assignments/grants made. Amount/currency limits, self-approval, assignment administrator and terms remain undecided; do not assume them.

Documents should follow photo retention. Actual photo code provides private server-authorized tenant/opening scope, immutable upload-operation/reservation identity, preservation of pending media through failures, and cleanup only after verified confirmation. It also exposes an explicit authorized deletion route: managed object is deleted before database row removal, failed deletion leaves a retry job; legacy rows without managed object identity can be removed directly. This is not a fixed-duration or perpetual-retention guarantee. The staging-specific scheduled worker is held; the explicit delete route still exists and has not been invoked.

No legal-hold, retention-duration, restore-window or blanket original-version retention policy was found in the reviewed photo lifecycle. Document history has an additional compatibility requirement: existing commercial adapter requires private immutable version bytes and estimate/warranty references must not silently change. Applying photo-style deletion blindly could break that evidence. Proposed conservative interpretation for approval: same private tenant access and failure-safe lifecycle; corrections create new versions, never overwrite prior bytes; keep referenced original versions unless an explicit compatible deletion/hold policy is settled. This is a proposal, not a new retention duration or activated WORM/legal-hold policy. No deletion worker, storage access or document adapter configuration changed.
